     1→     1→# RMIS v3.8 — Functional Flow Specification (UI-Agnostic)
     2→     2→
     3→     3→**System:** RMIS — Recruitment Management Information System for **DOST-MIRDC** (Metals Industry Research and Development Center, a Philippine government R&D agency under the Department of Science and Technology).
     4→     4→**Source of truth:** reverse-engineered 1:1 from the production codebase (`mi7sudev/RMISv3.8` — Next.js 16 / TypeScript / Prisma / SQLite).
     5→     5→**Purpose of this document:** a complete, self-contained behavioral specification of the system's **flows, data, rules, and contracts** so that another AI agent can rebuild the entire application — its **UI, UX, theme, styling, and layout are yours to design from scratch**. Nothing in this document constrains visual presentation.

     9→     9→## 0. How to Read This Document (Ground Rules for the Rebuilding Agent)
    10→    10→
    11→    11→1. **This spec intentionally omits ALL presentation concerns** — no colors, typography, spacing, components, or layout are specified. You have 100% freedom on UI/UX/theme/styling/layout.
    12→    12→2. What you MUST reproduce faithfully:
    13→    13→   - The **actor model** and what each role can see/do.
    14→    14→   - The **flows** (step order, gates, branches) as described.
    15→    15→   - The **data** each flow collects, displays, and exchanges.
    16→    16→   - The **business rules** (MQR evaluation, profile completeness, status machine, deadline visibility, notification doctrine).
    17→    17→   - The **API contracts** (paths, methods, payloads, status codes, and the *exact* error-message wording flagged as a "wording contract").
    18→    18→   - The **client behavior contracts** (polling cadence, session refresh triggers, deep-link/alias handling) — these are functional, not visual.
    19→    19→3. Where this document quotes a server message verbatim (in `"code spans"`), treat the wording as a **contract** — other logic branches on it.
    20→    20→4. Navigation model (functional): the production app is a **single-page application with one route (`/`)** and a **hash-based router** of the form `#/view?param=value&...`. Views are switched client-side per role. You may implement navigation differently, but the *set of views per role*, their *entry conditions*, and their *deep-link parameters* must be preserved. View keys and aliases are listed in §16.
    21→    21→5. Data storage conventions in production (SQLite, legacy Strapi-era naming) are documented in §5 for fidelity, but a rebuild may normalize storage **provided** every entity, field, and behavior in §5 and §6 is preserved.

    25→    25→## 1. System Identity & Purpose
    26→    26→
    27→    27→RMIS digitizes government recruitment end-to-end for MIRDC:
    28→    28→
    29→    29→1. **Applicants** register, build a **7-part profile** (Personal / Education / Work Experience / Training / Eligibility / Awards / Supporting Documents) — manually or by **uploading a CSC Personal Data Sheet (PDS, CS Form 212)** which the system auto-parses (deterministic parser, with AI fallback) and auto-fills into the profile.
    30→    30→2. Applicants **browse open job postings**, get **automatically screened against Minimum Qualification Requirements (MQR)**, and submit applications. Credentials are **snapshotted (frozen)** at apply time.
    31→    31→3. **HR/Evaluators** review applications against the frozen snapshots, **shortlist or reject**, and the system sends **status notices, regret letters, interview invitations, and skills-exam notices** (email + SMS + in-app).
    32→    32→4. **System intervention deliberately ENDS at the shortlist/reject notification.** Interviews, exams, and selection are conducted **face-to-face, offline** (per HR Minutes-of-Meeting 2026-09-03 policy).
    33→    33→
    34→    34→Core loop (the 5-step MOM process the system implements):
    35→    35→
    36→    36→```
    37→    37→1. Applicant submits application via RMIS
    38→    38→2. RMIS auto-evaluates minimum qualifications (MQR gate)
    39→    39→3. HR reviews qualified applicants and shortlists
    40→    40→4. System sends automated regret letters (not shortlisted)
    41→    41→5. System sends interview invitations / skills-exam notices (shortlisted)
    42→    42→   — everything after this point is offline
    43→    43→```
    44→    44→
    45→    45→Technology context (for orientation only; the rebuild may re-platform): Next.js 16 App Router (React 19), TypeScript, Tailwind + shadcn/ui, SQLite via Prisma ORM (single file `db/production-data.db`), custom JWT auth (`jose`) + bcryptjs, separate audit SQLite file (`db/audit.db`), AI extraction via any OpenAI-compatible API (default NVIDIA), filesystem document storage under `upload/<applicantId>/`.

    49→    49→## 2. Actor Model & Access Control
    50→    50→
    51→    51→### 2.1 Roles
    52→    52→
    53→    53→| Role | Who | Purpose | Home view after sign-in |
    54→    54→|---|---|---|---|
    55→    55→| **ADMIN** | HR staff (full authority) | Everything an evaluator can do, PLUS user management, settings (email/SMS providers), audit log, command center, analytics | `operations` (Command Center) |
    56→    56→| **EVALUATOR** | HR staff (reviewer) | Review queue, application review/decisions, notices, bulk regrets, direct email, assessments, job posting CRUD, candidate registry, jobs board | `review-queue` |
    57→    57→| **APPLICANT** | Public job seekers | Register, profile, PDS upload/extraction, browse/apply, track/cancel own applications | `home` |
    58→    58→| **Anonymous** | Not signed in | Public landing, job board (read-only), sign-in/sign-up | `home` (landing) |
    59→    59→
    60→    60→Role derivation (production data model): a user is ADMIN if `is_admin` flag is set; APPLICANT if linked to role id 3 (`applicants`); **EVALUATOR is the default for everyone else**. Admins can do everything evaluators can (evaluator guard = EVALUATOR **or** ADMIN).
    61→    61→
    62→    62→### 2.2 Two-Tier Network Access (staff intranet lock)
    63→    63→
    64→    64→- **Applicants/anonymous:** may access from any network (public internet).
    65→    65→- **Staff (ADMIN + EVALUATOR):** restricted to the **agency intranet** (private/loopback/CGNAT/link-local/IPv6-ULA IPs, or IPs in the `INTRANET_CIDRS` allowlist). Enforced at **three** independent chokepoints (defense in depth):
    66→    66→  1. `POST /api/auth/login` — staff login from a public IP → `403` + audit `LOGIN_BLOCKED_EXTERNAL`;
    67→    67→  2. `GET /api/session` — a staff session cookie resolved from a public IP returns `user: null` (fail closed) + audit `STAFF_ACCESS_BLOCKED_EXTERNAL`;
    68→    68→  3. Every guarded staff API call → `403` with a message explaining the intranet/VPN requirement.
    69→    69→- IP classification uses the **last** entry of `X-Forwarded-For` (proxy-vouched, spoof-resistant), then `X-Real-IP`. Kill switch: `INTRANET_ENFORCEMENT=off`.
    70→    70→
    71→    71→### 2.3 Permission Matrix (API level)
    72→    72→
    73→    73→| Capability | Anonymous | APPLICANT | EVALUATOR | ADMIN |
    74→    74→|---|---|---|---|---|
    75→    75→| Public landing, job board (GET jobs), health, reference data | ✔ | ✔ | ✔ (intranet) | ✔ (intranet) |
    76→    76→| Register / sign-in / sign-out | ✔ | ✔ | ✔ (intranet) | ✔ (intranet) |
    77→    77→| Session read | ✔ (null rules) | ✔ | ✔ (intranet) | ✔ (intranet) |
    78→    78→| Create/edit/delete job postings | ✗ | ✗ | ✔ | ✔ |
    79→    79→| MQR pre-check, apply, cancel own application, own profile CRUD, own documents, extraction | ✗ | ✔ | ✗ | ✗ |
    80→    80→| File downloads | ✗ | own files only | any | any |
    81→    81→| Evaluator queue, application detail, status decisions, notices, bulk regrets, direct email, assessments | ✗ | ✗ | ✔ | ✔ |
    82→    82→| Applicant master registry (`/api/admin/applicants`), positions management | ✗ | ✗ | ✔ | ✔ |
    83→    83→| User management, eligibility registry, stats, audit logs, email/SMS panels | ✗ | ✗ | ✗ | ✔ |

    87→    87→## 3. Session & Authentication
    88→    88→
    89→    89→### 3.1 Session model
    90→    90→
    91→    91→- JWT (HS256) containing `{ id, email, name, role }`; secret from `NEXTAUTH_SECRET`.
    92→    92→- Transported in an httpOnly cookie named `next-auth.session-token` (also accepts `__Secure-` prefix on read), `sameSite=lax`, `path=/`, 24-hour expiry; `secure` flag only when the request is HTTPS (plain-HTTP intranets must work).
    93→    93→- Login accepts **username OR email** as the identifier (case-insensitive on email).
    94→    94→
    95→    95→### 3.2 `GET /api/session` (bootstrap)
    96→    96→
    97→    97→Returns `{ user: null }` for: no session; staff resolved from a non-intranet network (audited); user deleted or `blocked`. Otherwise:
    98→    98→
    99→    99→```json
   100→   100→{
   101→   101→  "user": {
   102→   102→    "id": "string", "email": "string", "username": "string",
   103→   103→    "role": "ADMIN|EVALUATOR|APPLICANT",
   104→   104→    "firstName": "string", "lastName": "string", "middleName": "string|null",
   105→   105→    "isActive": true,
   106→   106→    "applicant": { "id": number, "isProfileComplete": boolean } | null
   107→   107→  }
   108→   108→}
   109→   109→```
   110→   110→
   111→   111→`applicant.isProfileComplete` is the **apply-gate flag** mirrored from the applicant record — it drives the applicant home banner and profile-completeness UX; every profile mutation must trigger a session refresh client-side.
   112→   112→
   113→   113→### 3.3 Sign-in flow (`POST /api/auth/login`)
   114→   114→
   115→   115→1. Body `{ identifier, password }`.
   116→   116→2. Rate limit: key = IP+identifier; **5 failed attempts per rolling 15 min**; on the 5th failure a **progressive lockout ladder** begins: 1 → 3 → 5 → 10 → 15 → 30 minutes; the escalation level is remembered until a successful login clears it.
   117→   117→3. Find user by email or username → bcrypt verify. Failure → `401 "Invalid credentials"` + audit `LOGIN_FAILED`.
   118→   118→4. Blocked account → `403 "Account is blocked"`.
   119→   119→5. Staff + non-intranet network → `403` (intranet message) + audit.
   120→   120→6. Success → audit `LOGIN_SUCCESS`, set cookie. Response: `{ id, email, username, role, firstName, lastName }`.
   121→   121→7. Client: toast welcome → session refresh → redirect to role home (ADMIN `operations`, EVALUATOR `review-queue`, APPLICANT `home`).
   122→   122→
   123→   123→### 3.4 Registration flow (`POST /api/auth/register`)
   124→   124→
   125→   125→- Rate limit: **5 per IP per hour** → `429`.
   126→   126→- Body: `{ email, firstName, lastName, password }`; password 6–128 chars. Duplicate email → `409`.
   127→   127→- Client-side additionally requires: password confirmation match and a **mandatory data-privacy consent checkbox** (RA 10173 compliance).
   128→   128→- Server (single transaction): create user (bcrypt cost 10, `is_applicant=true`, confirmed, not blocked, auto-username from email local part with numeric suffix dedupe) → role link (role id 3) → create **applicant profile row** → user↔applicant link.
   129→   129→- `201` → `{ id, email, role: "APPLICANT", applicantId }`.
   130→   130→- **Client flow: auto-login immediately after registration** (login with the email), session refresh, then navigate to the **profile builder** (new applicants land there, not home). Fallback to sign-in if auto-login fails.
   131→   131→
   132→   132→### 3.5 Sign-out (`POST /api/auth/logout`)
   133→   133→
   134→   134→Audits `LOGOUT`, expires the cookie with identical flags. Client: fire-and-forget (does not block navigation) → session refresh → navigate to sign-in.

   138→   138→## 4. Application Status Machine (Single Source of Truth)
   139→   139→
   140→   140→### 4.1 Canonical pipeline
   141→   141→
   142→   142→```
   143→   143→Applied ──→ Under Review ──→ ┌→ Shortlisted   (terminal in-system; interview is offline)
   144→   144→                             └→ Rejected      (terminal)
   145→   145→```
   146→   146→
   147→   147→- The **in-system pipeline ends at the decision**. Interview scheduling, skills exams, and selection happen face-to-face; the system only *notifies*.
   148→   148→
   149→   149→### 4.2 Stored values & normalization
   150→   150→
   151→   151→The database contains mixed spellings (production Title Case + legacy UPPER_CASE). The status vocabulary module normalizes everything:
   152→   152→
   153→   153→| Stored values (all aliases) | Canonical label | Semantics |
   154→   154→|---|---|---|
   155→   155→| `""`/DRAFT | Draft | neutral |
   156→   156→| `Applied`, `APPLIED` | **Applied** | submitted, not yet picked up |
   157→   157→| `Pending`, `PENDING` | Pending | treated as Applied stage |
   158→   158→| `Under Review`, `UNDER_REVIEW`, `For Evaluation`, `FOR_EVALUATION`, `Screening`, `SCREENING`, `Evaluation`, `EVALUATION`, `Final Review`, `FINAL_REVIEW`, `Evaluated`, `EVALUATED` | **Under Review** | evaluator has picked it up (all legacy spellings unify) |
   159→   159→| `Shortlisted`, `SHORTLISTED`, `Interview`, `INTERVIEW`, `Selected`, `SELECTED`, `Approved`, `APPROVED` | **Shortlisted** | passed; notice sent |
   160→   160→| `Rejected`, `REJECTED`, `Declined`, `DECLINED` | **Rejected** | not shortlisted |
   161→   161→| `Withdrawn`, `WITHDRAWN` | Withdrawn (Rejected stage) | |
   162→   162→| `Needs Correction`, `NEEDS_CORRECTION` | Needs Correction | |
   163→   163→| `Open`/`CLOSED` | (job-related legacy values) | |
   164→   164→
   165→   165→### 4.3 Writable statuses & transition rules
   166→   166→
   167→   167→- **API-writable (`SETTABLE_STATUSES`)** — only 4 values, in both spellings: `Applied | Under Review | Shortlisted | Rejected`. Enforced by validation (`statusUpdateSchema` with optional `reason` ≤500). **Only EVALUATOR/ADMIN** can write status. Applicants can never set status.
   168→   168→- There is **no explicit transition table** — any settable status may be written; correctness is enforced by *notification doctrine* (§9.3) and *notice stage guards* (§7.12):
   169→   169→  - Writing literal `"Applied"` = **silent revert**: no SMS, no email, no notification.
   170→   170→  - `Under Review` = explicit "Start Review" pick-up → dedicated under-review email + status SMS.
   171→   171→  - `Shortlisted` → flagship shortlist email + status SMS.
   172→   172→  - `Rejected`/`Declined` → **formal regret letter** email, **no** status SMS.
   173→   173→- **Applicant cancel:** only while status is exactly `Applied` (see §7.9).
   174→   174→- **Filterable statuses (`QUERYABLE_STATUSES`)** for the evaluator queue: 10 values × 2 spellings (Applied, Pending, Under Review, For Evaluation, Screening, Evaluation, Evaluated, Final Review, Shortlisted, Rejected, Interview, Selected, Approved, Declined, Needs Correction family); absent/invalid filter returns ALL. Queue ordering: **FIFO by application date ascending**.

   178→   178→## 5. Data Model (Functional Entity Catalog)
   179→   179→
   180→   180→> Field lists are the functional source of truth. Production physical names are given in parentheses when the naming is non-obvious. FKs are by naming convention; ordering of child collections is preserved via float `*_ord` columns on junction tables (production writes epoch-ms timestamps there).
   181→   181→
   182→   182→### 5.1 User (`up_users`)
   183→   183→
   184→   184→`id`, `username`, `email`, `password` (bcrypt), `firstName`, `middleName`, `lastName`, `is_admin` (bool), `is_applicant` (bool), `blocked` (bool — deactivation flag), `confirmed` (bool), `information_fillouted` (bool), `otp`, `encrypted_id`, `no_of_attemps` (login throttling), Strapi scaffolding timestamps. **Never expose** password/otp/tokens in any API.
   185→   185→
   186→   186→### 5.2 Applicant (`applicants`) — ~90 fields, the 7-part profile
   187→   187→
   188→   188→**Identity:** `employee_number`, `first_name`, `middle_name`, `last_name`, `extension_name`, `nickname`, `employee_id`
   189→   189→**Contact:** `mobile_number` (BigInt), `contact_number`, `contact_number_secondary`, `telephone_number`, `email_address`
   190→   190→**Personal:** `birth_date` (TEXT "YYYY-MM-DD"), `birth_place`, `gender`, `civil_status`, `citizenship`, `height`, `weight`, `blood_type`, `religion`, `ethnicity`, `is_pwd` (bool)
   191→   191→**Government IDs:** `pagibig`, `gsis`, `philhealth`, `tin`, `sss`, `govt_issued_id`, `govt_id_issued_number`, `govt_id_issued_place`, `govt_id_date_issued`, `govt_id_valid_until`
   192→   192→**Present address:** `house_number`, `street`, `subdivision`, `barangay`, `city`, `province`, `country`, `zip_code`, `present_address`
   193→   193→**Permanent address:** `permanent_*` set (+ `permanent_zip_code`, `permanent_telephone_number`)
   194→   194→**Declarations:** `is_government`, `pending_cases`, `admin_case` + `admin_case_details`, `crime_charge` + `crime_date` (TEXT) + `crime_case_status`, `character_reference` (**JSON array**: name, title, company, companyAddress, email, contact — 1..5 entries), `specify_referral`, `remarks`
   195→   195→**Workflow:** `qualified`, `institution`, `application_status` (⚠️ legacy BOOLEAN, unrelated to the application status machine), `submitted_date`, **`is_fillouted`** (bool — THE profile-complete gate flag), `status_of_eployment` (legacy typo), `respondent_to`
   196→   196→**Legacy single-file attachment paths:** `image_path`, `application_letter_path`, `pds_path`, `employment_certificate_path`, `tor_path`, `coe_path`, `training_certificate_path`, `info_sheet_path`, `curriculum_vitae_path`, `performance_path`, `wexp_path` (coexist with the modern document store §10)
   197→   197→
   198→   198→### 5.3 Profile sub-entities (each: content table + applicant junction with `*_ord` ordering)
   199→   199→
   200→   200→| Entity | Key fields |
   201→   201→|---|---|
   202→   202→| **Education** | `education_level` (Elementary/Secondary/Vocational/College/Graduate — plus "Senior High School" concept), `degree`, `course`, `specify_others`, `school_name`, `ongoing` (bool), `is_highest_education`, `year_from`/`year_to` (TEXT), `highest_level`, `units_earned`, `year_graduated` (TEXT), `awards`, `hr_remarks` |
   203→   203→| **Work Experience** | `position_title`, `employer_name`, `employer_address`, `is_present_work`, `is_govt_service`, `inclusive_date_from/to` (datetime), `status_of_employment`, `monthly_salary` (float), `supervisor_name/position`, `office`, `reason_for_leaving`, `accomplishment`, `actual_duties`, `hr_remarks`, **`year_decimal`** (float — computed years used by MQR: derived from inclusive dates with 365.25-day years; open-ended = until today) |

   208→   208→
   209→   209→### 5.4 Position (`postions` — table typo preserved) — the plantilla item + CSC standards
   210→   210→
   211→   211→- `item_number`, `position_title`, `position_type`, `position_status`, `position_salary_grade` (string), `position_salary_step` (string; wire name `salaryStep` — documented rename trap), `position_salary_amount`, `salary_grade`, `salary_amount` (float), `position_level` (int), `division_id` (BigInt), `place_of_assignment_id` (+ junction), `office_id`, `department_id`, `section_id`, `date_vacated`, `incumbent_id`, `years_required`, `hours_required`, `special_skill` / license, `preferred_qualification`, `competency_requirements` (+ richtext JSON)

   213→   213→  - `csc_education` (verbatim requirement text, e.g. "Bachelor's degree relevant to the job")
   214→   214→  - `csc_eligibility` and `csc_eligibility_group` (e.g. "Career Service Professional", "RA 1080 (Bar/Board)", "N/A")
   215→   215→  - `csc_work_experience` (e.g. "1 year of relevant experience" — quantity parsed)
   216→   216→  - `csc_training_requirements` (e.g. "Sixteen (16) hours of relevant training")
   217→   217→- Legacy free-text mirrors: `education`, `experience`, `training`, `eligibility`, `division`, `section`.
   218→   218→
   219→   219→### 5.5 Job Posting (`jobpostings`) — the vacancy as published
   220→   220→
   221→   221→- `position_type`, `number_of_vacancy` (int), `brief_description` (+ `brief_description_richtext`), `duties_responsibilities` (+ richtext), `compensation_package` (+ richtext), `other_qualifications` (+ richtext), `publish_date`, `deadline_date`, `processing_date`, `contract_date_from/to`
   222→   222→- Linked to a Position via junction `jobpostings_postions_lnk` (first-by-ord wins). Authored by a staff user.
   223→   223→- **Rich-text pairs:** plain textarea values are stored alongside sanitized HTML companions (`*_Html` fields) — HTML is sanitized server-side (allowlist; strips scripts/iframes/inline handlers/`javascript:`/styles/`data-*`; forces links to `target=_blank rel=noopener noreferrer`).
   224→   224→
   225→   225→### 5.6 Application (`applications`)
   226→   226→
   227→   227→- `date_applied` (datetime), `application_status` (string — the status machine §4)
   228→   228→- **7 snapshot JSON columns** (the frozen credentials, written via raw SQL because they are `Unsupported("json")` in Prisma):
   229→   229→  - `snapshot_profile`: id, firstName, lastName, emailAddress, contactNumber, gender, civilStatus, citizenship, birthDate, presentAddress, city, province, country, + characterReference (parsed array)
   230→   230→  - `snapshot_educations`, `snapshot_experiences`, `snapshot_trainings`, `snapshot_eligibilities`, `snapshot_awards`: full entry arrays
   231→   231→  - `snapshot_attachment`: attachment metadata (legacy)
   232→   232→- Linked to applicant and job posting via junction tables (`applications_applicant_lnk`, `applications_job_lnk`).
   233→   233→- **Snapshots are the reviewer's source of truth** — the live profile may drift after applying; reviewer surfaces must read snapshots. MQR results are **never persisted** (recomputed on demand).
   234→   234→
   235→   235→### 5.7 Evaluation artifacts
   236→   236→
   237→   237→- **Interview Assessment** (`applicant_interview_assessments`): 11 integer 1–10 ratings each with a comment — education, work_experience, training, eligibility, technical_skills, organizational_awareness, interpersonal_skills, adaptability, extra_curricular, personal_development, technology_application — plus `overall_assessment_rating` (Outstanding / Very Satisfactory / Satisfactory / Fair / Unsatisfactory), `comment_and_recommendation`, `type_of_application`, `year`. Linked to applicant, interviewer, position.
   238→   238→- **Interviewer** (`interviewers`): find-or-create by user name, position "Evaluator".
   239→   239→- **Interview** (`applicant_interviews`): date/mode/place/remarks/notified/zoom_link/type/year (offline workflow record).
   240→   240→- **Examination** (`applicant_examinations`): date/place/rating/psychosocial_test/mode/notified/type/year.
   241→   241→
   242→   242→### 5.8 Notifications & message logs
   243→   243→
   244→   244→- **In-app Notification** (`notifications`): `name`, `notification_description`, `notification_date` (TEXT), linked to an applicant via junction — used for status changes, notices, bulk regrets. (Historically also carried audit rows `name LIKE "[AUDIT]%"` — since migrated.)
   245→   245→- **`email_logs`**: to, subject, body_text, body_html, provider, status (`sent|failed|mock|skipped`), provider_ref, error, related_type/related_id (e.g. `"application"`, `"application-direct"`, `"test"`), attachments (metadata only: name+bytes), created_at.
   246→   246→- **`sms_logs`**: to, message, provider, status (`sent|failed|mock`), provider_ref, error, related_type/related_id, created_at.
   247→   247→- Subject **prefixes double as idempotency keys** (e.g. `"Application regret — "` ⇒ already-sent detection for bulk regrets; notice history queries email_logs by subject prefixes).
   248→   248→

   250→   250→

   284→   284→## 6. Complete API Surface (Contract Reference)
   285→   285→
   286→   286→Conventions:
   287→   287→- Envelope: success returns the payload JSON directly (HTTP 200/201); failure returns `{ "error": string, "details"?: object }` with 400/401/403/404/409/413/415/429/500/502. Unexpected exceptions always collapse to a generic 500 (never leak internals).
   288→   288→- Pagination: `?page` (≥1), `?pageSize` (1–100, default 50) → `{ data, total, page, pageSize, hasMore }`.
   289→   289→- Body convention `body.data ?? body`. Dates accepted as `YYYY-MM-DD` or full ISO. Numeric IDs parsed strictly (NaN → 400).
   290→   290→- **No middleware** — every route re-asserts auth + role + intranet tier itself.

   392→   392→### 7.4 Profile builder — the 7-part applicant profile (`#/profile`)
   393→   393→
   394→   394→Functional structure (all presentation free):
   395→   395→
   396→   396→- **Header:** avatar (from latest PROFILE_PICTURE document; replaceable), name, completeness status (Complete/Incomplete), a **completion ring = filled sections / 7**, "Mark Complete" action when eligible, document count, and an "AI-assisted" indicator while extraction is active.
   397→   397→- **Section navigation:** numbered 01–07 with per-section completeness indicators and a "Section X of 7" readout; works on mobile (stepper) and desktop (sticky list).
   398→   398→- **Data loading:** parallel fetch of profile + reference data (eligibilities, courses, places of assignment) + own documents.
   399→   399→
   400→   400→**Section 01 — Personal Information** (4 disclosure groups, each with "X of N completed" summaries):
   401→   401→- *Identity:* First name*, Middle name, Last name*, Extension name, Email address* (helper: "interview invites are sent here"), Mobile number (helper format `09XXXXXXXXX`, 11 digits), Secondary contact, Birth date, Birth place, Gender (Male/Female), Civil status (Single/Married/Widowed/Separated/Divorced), Citizenship, Religion, PWD toggle (Yes/No), Ethnicity.
   402→   402→- *Address:* present address block (house no., street, subdivision, barangay, city, province, country, ZIP).
   403→   403→- *Legal disclosures:* administrative offense Yes/No → conditional details; criminal charge Yes/No → conditional date filed + case status.
   404→   404→- *Character references:* 1–5 entries (add capped at 5; remove floors at 1), each: name, title, company, company address, email, contact. Empty-name entries filtered at save.
   405→   405→- **Autosave:** every change re-arms a **1.2 s debounce** → `PUT /api/applicant/profile`, with a live save-state indicator (Saving… / Changes saved / Save failed — retry). An explicit Save action exists (and a mobile fixed save affordance while dirty). Save triggers a session refresh.
   406→   406→
   407→   407→**Sections 02–06 — Education / Work Experience / Training / Eligibility / Awards** (identical functional pattern: list of entry cards + add/edit form + delete):
   408→   408→- *Education:* Education level select (incl. Vocational/Trade), Course/Degree, School name*, Year graduated, Units earned, Awards/honors.
   409→   409→- *Work experience:* Position title*, Employer name*, Employment status select, Employer address, Date from/to, "Currently employed here?" (clears Date to), Monthly salary (number), Government service Yes/No, Actual duties.
   410→   410→- *Training:* Title*, Type select, Number of hours, Date from/to.
   411→   411→- *Eligibility:* **spec-driven selection** from the CSC eligibility registry (merged with reference data). Choosing a type reveals only its relevant fields — exam-based → Rating / Exam date / Exam place; Bar/Board → + License no. / Validity; conferment-based → Date/Place of Conferment; "Others" → one free-text title. The saved title must match the job's required eligibility vocabulary for MQR matching.
   412→   412→- *Awards:* Recognition type (Award/Accomplishment), Scope (Individual/Group vs Local/Foreign/International), Details*, Category, Awarding body, Date granted.
   413→   413→- Mutations: create via POST; **edit = delete + recreate** (no update endpoints); deletes confirm; toasts on every outcome; optimistic local updates with "pending-" placeholder ids for unsaved extraction data.
   414→   414→- **Mark Complete:** confirm dialog stating the profile will be "ready for application… subject to verification by HR" → `PUT profile { isProfileComplete: true }` (server re-validates §8.3) → session refresh.

   420→   420→
   421→   421→Pipeline (with phase progress: Uploading 30% → Extracting 70% → Applying 90%):
   422→   422→
   423→   423→1. **Upload** the PDS file (drag or picker; accepted: `.pdf .png .jpg .jpeg .gif .webp .doc .docx .xlsx .xls .xlsm`, ≤10 MB) → `POST /api/applicant/documents` (category PDS).

   527→   527→## 8. Business Rules Engines
   528→   528→
   529→   529→### 8.1 MQR apply gate (`mqr.ts`) — binary, MOM-vocabulary
   530→   530→
   531→   531→`verifyMqr(applicant, position)` → verdict strings per dimension. Success string is mandated verbatim: `"Meets the minimum requirements"`; failure: `"Does not meet the minimum requirements"` (+ diagnostic). `allMet` = all four equal the success string. **Enforced server-side at apply; fast-track cannot bypass; results are never persisted.**
   532→   532→
   533→   533→| Dimension | Rule |
   534→   534→|---|---|
   535→   535→| **Education** | Tokenize requirement (`csc_education`) and every applicant education entry (`course + specify_others`), lowercase, strip non-alphanumerics, drop generic stop-words (bachelor(s), degree, of, in, arts, major, minor, course, program, career, service, to, the, science). Pass if requirement empty **or** contains "relevant" (then any education passes — HR judges relevance). Otherwise pass if **≥ min(2, #required tokens)** match. **Substitution:** holding any "bachelor" credential lowers the threshold to **≥ 1 matched token**. |
   536→   536→| **Eligibility** | Requirement text = `csc_eligibility_group`. Empty / `N/A` / `NA` / `None` → pass (not required). Generic boilerplate ("Career Service Professional", "Second Level Eligibility" — all stop-words) → pass iff applicant holds **≥1 eligibility of any kind**. Otherwise **every** required token must appear in some eligibility title (subset match). |
   537→   537→| **Work experience** | Required years = first number in `csc_work_experience` (parenthesized form wins: `"(4)"` beats bare digits). Applicant years = **Σ `year_decimal`** across all work entries (no relevance filter). Pass: `total ≥ required`. |
   538→   538→| **Training** | Required hours extracted identically from `csc_training_requirements`. Applicant hours = Σ (`hour_decimal` ?? `number_hours`). Pass: `total ≥ required`. |
   539→   539→
   540→   540→### 8.2 Reviewer-side requirements report (`requirements.ts`) — honest-uncertainty engine
   541→   541→
   542→   542→Recomputed **live** from the application **snapshots** vs the **live** position `csc_*` columns (never persisted — profiles can drift). Per-check status vocabulary: **`MET | NOT_MET | NOT_REQUIRED | REVIEW`** (ambiguous standards → REVIEW, "never silently fails the applicant"). Report verdicts: **`ALL_MET | PARTIAL | NONE_MET | NEEDS_REVIEW | NO_REQUIREMENTS`**.
   543→   543→
   544→   544→- "Not required" detector: blank, N/A, na, none, "none required", "not required" → excluded from requiredCount.
   545→   545→- Bare-number standards (legacy rows) → REVIEW for education/experience/training.
   546→   546→- Quantity extraction: parenthesized `(4)` → "4 hours" digit+unit → word numbers (one…fifteen, twenty, twentyfour, forty, eighty, hundred) → 0; a standard with no year/hour word at all → REVIEW.
   547→   547→- **Experience:** Σ years per row from `year_decimal`, else derived from inclusive dates (365.25-day years; open-ended rows count to today). NOT_MET quantifies the shortfall ("0.5 more years of relevant experience needed") with up to 3 evidence lines.
   548→   548→- **Education clause parser:** requirement split on ` or ` / `;` into alternatives; each parsed to `{ minLevel, partialCollege, tokens }`. Level detection: post-grad/PhD=6, master's=5, **vocational/trade/technical=3 (checked before bachelor)**, bachelor/BS/BA/AB/college/degree=4, high school/SHS/grade 12=2, elementary=1; "two years in college" ⇒ level 4 + partialCollege (ongoing college counts). Course tokens suppressed entirely when the clause contains "relevant". A row matches if level ≥ minLevel AND completion (not ongoing / graduated year present) AND any course token appears in the row's course/degree text.
   549→   549→- **Eligibility alternatives:** split on `/ , ; or` (commas inside parens protected); classify each: RA 1080 / Professional / Sub-Professional / named / unparseable. Matching: professional ⇐ applicant eligibility level ≥ 5 OR name contains "professional" (not "sub") OR name encodes RA 1080 (board license counts as professional-class); sub ⇐ level ≥ 2 OR sub/first-level/professional naming; ra1080 ⇐ compact name contains `ra1080`; named ⇐ token substring. Specific-eligibility rows with numeric levels also count.
   550→   550→
   551→   551→### 8.3 Profile completeness (the government apply gate)
   552→   552→
   553→   553→Exactly **3 requirements**, all-or-nothing (no weights):
   554→   554→1. **Personal** — first name AND last name AND email address non-empty;
   555→   555→2. **Education** — ≥ 1 education entry;
   556→   556→3. **Work experience** — ≥ 1 work experience entry.
   557→   557→
   558→   558→Enforced at **three** points: `PUT profile` (granting the flag), `POST profile/complete` (fast-track), and **`POST jobs/apply` re-validation** (flag AND live re-check — an emptied-but-flagged profile cannot apply). Error wording contract: `"Please complete your profile before applying. Still required: {missing}."` — the jobs client routes messages matching `/complete your profile/i` into the fast-track. Corrupted section reads degrade to "not met" (never 500).
   559→   559→
   560→   560→### 8.4 Extraction auto-apply semantics (`/api/applicant/profile/auto-apply`)
   561→   561→
   562→   562→Input: `{ extraction: { personalInfo?, educations?, workExperiences?, trainings?, eligibilities?, awards? } }` where array items use `{ field: { value, confidence } }` shape.
   563→   563→- **Personal info = OVERRIDE:** an 18-field allowlist is overwritten with extracted values (birth date → ISO text; mobile → digit-strip → BigInt); entries with confidence `"none"`/empty are skipped.
   564→   564→- **Each section = REPLACE (delete-all + recreate) only when the extraction contains ≥ 1 entry** — zero entries ⇒ existing data kept (empty ≠ "no data").
   565→   565→- Row anchors required (education: school/course/degree; work: position/employer [+ server-computed yearDecimal]; training: title; eligibility: title/license/rating — title resolved via find-or-create draft reference row; award: details/type/provider).
   566→   566→- After writes, recompute profile completion. Response: `{ applied, replaced, totalFilled, totalReplaced, profileCompletion, message }`.
   567→   567→
   568→   568→### 8.5 Deterministic PDS parser (primary path for PDS × Excel)
   569→   569→
   570→   570→Recognizes **CSC Form 212** (2017 & **Revised 2026** layouts) by sheet fingerprints. Strategy: **label-anchored scanning** (find the label cell → scan rightward within bounds for the first non-noise value). Noise filters: ~200-country name set, dropdown options, bare Yes/No (2026 checkboxes), form furniture (continuation markers, "CS FORM 212", "page N of N", SIGNATURE/DATE rows, parenthetical instructions, section headers I.–XII., "do not abbreviate", etc.).
   571→   571→
   572→   572→- **Sheets:** C1 = personal + family + education; C2 = eligibility + work; C3 = training + voluntary + other/awards; C4 = disclosures/references; continuation sheets classified by header keywords or **table-shape sniffing** (applicant-made continuation layouts recovered; official blank continuation pages excluded); unclassifiable sheets → warning surfaced to the reviewer.
   573→   573→- **Personal:** surname/first/middle/extension, birth date (sanity-normalized 1900–2200), birth place, sex (domain-checked male|female), civil status (domain-checked), citizenship, residential address block (city/province read from the row above the sub-label — known layout quirk), ZIP, mobile, email (must contain `@`).
   574→   574→- **Education table:** level column patterns (ELEMENTARY/SECONDARY/VOCATIONAL/COLLEGE/GRADUATE), school, degree/course, period, year graduated, honors; "GRADUATED" in the degree column ⇒ units="GRADUATED", degree null; scan bounded by markers (supports overflow rows).
   575→   575→- **Eligibility table:** columns auto-detected from header text (2017 vs 2026 layouts differ: rating/exam date/place/license/validity positions).
   576→   576→- **Work table:** Mode A (official header) + Mode B (**applicant-made continuation layout** recovered by column-shape: counter, from, to, position >8 chars, employer, salary, status, govt).
   577→   577→- **Training table:** Mode A (official: title, dates, hours with " HOURS" suffix stripping, type) + Mode B (continuation shape, gated by date/hours-shaped cells).
   578→   578→- **Awards:** anchored on "NON-ACADEMIC DISTINCTIONS", scan to "MEMBERSHIP"; per-row first valid cell → recognition type "Recognition".
   579→   579→- Invariants: blank official template ⇒ **0 fields extracted** (tested); duplicates deduped by signature (training: title|from; award: details; work: title|employer|from; eligibility: title|examDate; education: level|school).
   580→   580→
   581→   581→### 8.6 AI extraction fallback (`extraction.ts` + `ai-client.ts`)
   582→   582→
   583→   583→- Trigger: PDS parsing returns null / non-PDS document types / images.
   584→   584→- Text extraction: Excel via exceljs (skip Lookup sheet, country-noise filter, merged-cell echo dedupe, 16K truncation); PDF per-page (unpdf); Word via mammoth (12K truncation for non-PDS).
   585→   585→- LLM: any OpenAI-compatible API. Defaults: base `https://integrate.api.nvidia.com/v1`, text model `nvidia/llama-3.3-nemotron-super-49b-v1`, vision `nvidia/nemotron-nano-12b-v2-vl`. Config via env (`AI_API_KEY`, `AI_BASE_URL`, `AI_TEXT_MODEL`, `AI_VISION_MODEL`). Missing key ⇒ extraction fails with a clear message; everything else keeps working.
   586→   586→- PDS-Excel fallback: 2 sequential LLM calls (sheet-split; 429 retry with 3/6/9 s backoff; section failure ⇒ empty section, never abort). PDS-PDF: page-chunked (≤4 pages / ≤11K chars per chunk, ≤40 pages; chunk 1 core + later chunks shape-classified continuation prompts; results merged + deduped). Images: single vision call per category prompt.
   587→   587→- Prompt contract (all templates): extract only what is clearly present; **never fabricate**; not found ⇒ value null + confidence "none"; confidence high/medium/low definitions; JSON only; "N/A" ⇒ empty array; dates → `YYYY-MM-DD`.
   588→   588→- Extraction status per doc: 0 fields → FAILED; <3 → PARTIALLY_EXTRACTED; else EXTRACTED (persisted on the sidecar). Safe, user-facing error mapping (file-read / not-configured / unreachable / generic).
   589→   589→
   590→   590→### 8.7 Job visibility & deadline rules
   591→   591→
   592→   592→- Public listing (non-staff viewers) hides a posting once `deadline_date < start-of-today` (date-level compare) — MOM rule: "removed from public listing the day after closing." Staff (ADMIN/EVALUATOR) always see all.
   593→   593→- Apply API independently **blocks** past-deadline submissions (400).
   594→   594→- Deadline urgency vocabulary used in flows: Open / Closing today / Closing in N days (≤7) / N days left (≤30) / Closed / "Open until filled" when no deadline.
   595→   595→
   596→   596→### 8.8 Snapshot freezing (apply time)
   597→   597→
   598→   598→On successful apply, the profile is frozen into the 7 snapshot JSON columns (§5.6) via raw SQL. Reviewer surfaces read **only** snapshots; key normalization (snake_case legacy → camelCase) is applied on read. Snapshots are deleted with the application (job cascade delete).

   608→   608→- **Hard contract:** `sendEmail`/`sendSms` **never throw** — notifications are fire-and-forget side effects; **every attempt is persisted** to `email_logs`/`sms_logs` with status `sent|failed|mock|skipped` (skipped = e.g. no valid address/phone), provider ref, error, relatedType/relatedId, attachment **metadata only** (name + bytes).
   609→   609→
   610→   610→### 9.2 In-app notifications
   611→   611→
   612→   612→Status changes, notices, and bulk regrets also create a Notification row linked to the applicant (`name`, `description`, date). The admin notifications panel derives its items from stats: **attention** ("N applications awaiting review", "N job deadlines this week"), **updates** ("N incomplete applicant profiles"), **system** ("N failed logins (24 h)") — informational, 30 s visible-tab poll, empty state "You're up to date".

   615→   615→
   616→   616→| Event | Email | SMS | In-app |
   617→   617→|---|---|---|---|
   618→   618→| Application submitted | — | "application received" notice | — |

   622→   622→| Any other settable status | generic status-change notice (+ optional HR reason) | generic status SMS (≤640 chars) | ✔ |
   623→   623→| Literal `"Applied"` write (silent revert) | none | none | none |
   624→   624→| Interview invitation (notice) | invitation template (date/time/venue table; TBA fallback; contact/notes) | companion SMS | ✔ |

   660→   660→
   661→   661→### 12.1 Rate limits (in-memory; reset on restart — documented stopgap)
   662→   662→| Scope | Rule |
   663→   663→|---|---|
   664→   664→| Login | 5 failures / rolling 15 min per IP+identifier → progressive lockout ladder 1→3→5→10→15→30 min; escalation remembered until a success clears it |
   665→   665→| Registration | 5 per IP per hour → 429 |
   666→   666→| Direct emails | 20 per user per 10 min → 429 (minutes-remaining message) |
   667→   667→
   668→   668→### 12.2 File constraints — see §10.
   669→   669→
   670→   670→### 12.3 Validation (Zod, shared client+server)
   671→   671→- Dates accept `YYYY-MM-DD` or ISO datetime (production dates are TEXT).
   672→   672→- Register: email, names ≤80, password 6–128. Users: username 3–60, role enum.
   673→   673→- Education: level ≤50, degree ≤120, course/school ≤200, yearGraduated ≤20, awards/hrRemarks ≤500. Work: position ≤200, monthlySalary 0–10,000,000, address ≤500, duties/accomplishment ≤2000. Training: hours 0–10000. Eligibility: title ≤200, rating ≤20, license ≤80. Awards: type/scope ≤30, details ≤500, points 0–1000.
   674→   674→- Job create: title 1–200, vacancy 1–99 default 1, rich-text caps (e.g. dutiesHtml ≤20000). Position: 19 fields (positionLevel 0–20, salaryAmount 0–1,000,000, CSC columns capped 200–1000).
   675→   675→- Status update: SETTABLE enum + reason ≤500. Assessments: 11 ratings int 1–10 + comments ≤2000 + overall enum.
   676→   676→- Zod failures → 400 with `details = zodError.flatten()`.
   677→   677→
   678→   678→### 12.4 Sanitization
   679→   679→`sanitizeHtml` (regex allowlist): strips script/style/iframe/object/embed/form/input/textarea/select/button/link/meta/base/svg/math content & tags, `on*` handlers, `javascript:` URLs (→ `href="#"`), all `data-*` and `style` attributes; non-allowlisted tags stripped keeping text; `<a>` forced to `target=_blank rel="noopener noreferrer"`. Applied to all admin-authored job rich text before storage.
   680→   680→
   681→   681→### 12.5 Error-handling posture
   682→   682→- `handleApi` wrapper: known `ApiError` → its message + status; unexpected → server console + generic 500. Client: network failure → "Unable to connect…" fallback; 4xx uses the server's route-authored message verbatim; 5xx always generic.

   742→   742→## 17. Glossary
   743→   743→
   744→   744→- **PDS** — Personal Data Sheet, CSC Form 212 (Revised 2017/2026), the Philippine government job-application spreadsheet.
   745→   745→- **MQR** — Minimum Qualification Requirements; the four CSC standards (education, experience, training, eligibility) attached to a position.
   746→   746→- **CSC** — Civil Service Commission (Philippines); source of eligibility/education requirement rules (e.g., MC 07 s. 2025 education equivalency).
   747→   747→- **SG / Salary Grade** — government pay banding shown on postings.
   748→   748→- **Snapshot** — the frozen copy of an applicant's credentials written into the application at apply time.
   749→   749→- **Fast-track** — the apply-while-incomplete flow: upload PDS → auto-fill → certify completeness → submit.
   750→   750→- **Stage** — the canonical pipeline grouping of any stored status spelling (Applied / Under Review / Shortlisted / Rejected).
   751→   751→- **Intranet tier** — the network-level restriction limiting staff accounts to agency networks.
   752→   752→- **Regret letter** — the formal "not shortlisted" notice (email; deliberately no SMS).
   753→   753→- **Notice** — interview invitation or skills-exam notification sent to shortlisted applicants.
